This document describes behavior implemented on the current default branch. Documents named
`technical-debt-analysis`, `architecture-improvements`, `performance-optimization`,
`future-enhancements`, and `improvements-index` are planning records, not current guarantees.

== Supported runtime

The tested source matrix is Python 3.12 and 3.13 with PySpark 3.5.9, PyDeequ 1.6.0,
and the Deequ `2.0.8-spark-3.5` JAR. PyDeequ 1.6.0 does not map Spark 4.x artifacts, so this
repository does not claim Spark 4 or Databricks Runtime 18 compatibility.

Install the framework path used by the orchestrator and built-in engines:

[source,shell]
----
pip install 'data-quality-framework[spark,deequ]'
----

Add `aws` for Glue/S3 support and `databricks` for the Databricks SDK integration. The Great
Expectations adapter imports `great_expectations` at runtime, but the project does not pin that
third-party package because the adapter uses its legacy `SparkDFDataset` API. Install and test a
compatible version explicitly before selecting that engine.

== Architecture

image::framework-overview.png[Framework components]

The active architecture assessment, debt ledger, and bounded delivery sequence are in
link:modernization-plan.adoc[Architecture Modernization Plan]. The governing incremental
design decision is
link:decisions/adr/ADR-001-incremental-typed-execution-kernel.adoc[ADR-001].

The implemented execution path is:

. `DQFramework` parses a HOCON string or supported URI.
. `CatalogFactory` selects the Spark, Hive, Unity/Delta, or Glue catalog provider.
. Configured DataFrames are resolved before rule execution; an optional default DataFrame can be
  supplied directly.
. `EngineLoader` accepts a lowercase alphanumeric/underscore engine name and imports
  `dq.engine.<name>.<name>_engine`.
. Each engine returns metric dictionaries. `DQFramework.run()` adds the execution timestamp and
  Spark application ID.
. When a rule supplies repository configuration, supporting engines can append metric and
  verification DataFrames to file paths or catalog tables.

The public base contract is:

[source,python]
----
class DQEngine(ABC):
    @abstractmethod
    def apply(self, dataframe: DataFrame, repository=None) -> list[dict]:
        ...
----

== Configuration loading

`DQFramework(spark, config, default_dataframe=None)` accepts:

* an inline HOCON string;
* `file://` for a local HOCON file;
* `s3://` when the AWS extra and credentials are available;
* `abfss://` in a Spark environment configured for ADLS Gen2; or
* `http://` or `https://` (the HTTP helper applies a request timeout).

Unknown URI schemes raise `ConfigurationError`. `dq-validate` fully parses local and `file://`
configuration; for remote schemes it currently emits a warning and does not fetch the document.

A minimal Deequ configuration is:

[source,hocon]
----
dqframework {
  dqrules = [
    {
      name = "completeness_checks"
      engine = "deequ"
      dataframes = ["default"]
      checks = [
        {
          constraint_name = "id_complete"
          constraint = "isComplete"
          column = "id"
          level = "Error"
        }
      ]
    }
  ]
}
----

Pass the DataFrame as `default_dataframe`, or declare table-backed frames:

[source,hocon]
----
dqframework {
  catalog_type = "unity"
  dataframes {
    orders = "main.sales.orders"
    customers {
      catalog = "main"
      database = "sales"
      table = "customers"
    }
  }
  dqrules = []
}
----

Table identifiers are limited to one-, two-, or three-part alphanumeric/underscore identifiers;
arbitrary SQL expressions are not accepted as table names.

== Catalog providers

`catalog_type` supports:

* `spark` (default fallback) and `hive`, both through Spark's catalog;
* `unity` and `delta`, through the Unity Catalog provider; and
* `glue`, through the AWS Glue provider.

When `catalog_type` is omitted, the factory checks Spark configuration for Unity/Delta or Glue
markers and otherwise selects `spark`. Catalog permissions and cloud credentials are supplied by
the runtime; the framework does not embed them.

== Engines

=== Deequ

The `deequ` engine maps supported HOCON constraints to PyDeequ checks and requires the matching
Deequ JAR on the Spark classpath. The checked-in local example uses:

[source,python]
----
SparkSession.builder \
    .config("spark.jars", "lib/deequ-2.0.8-spark-3.5.jar") \
    .getOrCreate()
----

=== Schema validation

The `schemavalidation` engine uses Deequ plus Spark schema inspection for datatype, nullable,
unique, and foreign-key checks. See `examples/schema_validation.conf`.

=== Custom constraints

The `custom` engine currently implements `DistinctnessByGroup`, `RateOfChange`,
`LookupBasedOnColumnNameList`, and `WideTablesNegativeValuesCheck`. See
`examples/custom_constraints.conf`.

=== Great Expectations adapter

The `greatexpectations` engine is an optional compatibility adapter. It requires a separately
installed Great Expectations release that still exposes `ge.dataset.SparkDFDataset`; current CI
tests the adapter boundary with a controlled substitute and does not certify a live external
Great Expectations/Spark combination.

== Results and repositories

`DQFramework.run()` returns a list of dictionaries containing at least `check`, `success`,
`details`, `ts`, and `jobid` for results emitted by an engine.

Repository configuration is optional. The current helper requires `dataset`, accepts formats
`parquet`, `csv`, `json`, `delta`, or `orc`, and supports:

[source,hocon]
----
repository {
  dataset = "orders"
  format = "delta"
  file {
    paths = ["/quality/results"]
  }
  catalog {
    tables = ["quality.orders"]
  }
}
----

The helper appends partitioned file results and appends to or creates catalog tables with metric
suffixes. It does not implement retries, alert delivery, retention, or access control; those are
deployment responsibilities.

== Command-line tools

[source,shell]
----
dq-framework file:///absolute/path/config.conf --spark-master 'local[*]'
dq-validate file:///absolute/path/config.conf --format json
----

`dq-framework` creates a Spark session, runs the configured checks, prints a summary, and returns
nonzero when checks fail. `dq-validate` validates required local configuration structure without
running Spark checks.

== Security boundaries

* Do not place cloud credentials, Databricks tokens, or storage secrets in HOCON files.
* Use runtime-native identity, secret managers, and least-privilege catalog/storage grants.
* Only HTTPS should be used for remote configuration in production.
* Table names are validated, but configuration content remains trusted operational input.
* Databricks automation should use OAuth machine-to-machine or workload identity federation.

See link:databricks-authentication.adoc[Databricks authentication and runtime compatibility].

== Tests and CI

CI runs the Spark-backed test suite on Python 3.12 and 3.13. It rejects missing tests,
enforces independent 55% line and branch floors, enforces changed-code coverage, runs Black,
Flake8, Bandit, and pip-audit, builds the package, reviews dependency changes, and checks
documentation links. A fail-closed aggregate job is the required branch-protection context.

The owner path runs only after immutable owner/repository checks and environment approval on
self-hosted capacity. Other pull requests stay on GitHub-hosted runners.
