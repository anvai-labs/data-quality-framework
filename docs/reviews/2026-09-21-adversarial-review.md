## Verdict per bet (1-6)

**BET 1 — RISKY-WITH-MITIGATION**

Single-version subplans preserve useful certification boundaries, but mixed rule packs are rejected and there is no parent contract requiring all subplans to finish against the same snapshot ([ADR-004:48](../decisions/adr/ADR-004-grouped-metric-requests.adoc#L48), [plan.py:387](../../dq/plan.py#L387), [test_portable_config.py:391](../../dq/tests/test_portable_config.py#L391)). Add a versioned ruleset envelope with expected child fingerprints and one aggregate verdict; this preserves existing fingerprints and per-version certification without making callers invent evidence joins.

**BET 2 — RISKY-WITH-MITIGATION**

Vacuous success is internally consistent and explicitly tested, but ranges also pass on a populated, entirely null/NaN column, so a positive row count alone does not protect admission ([plan.py:546](../../dq/plan.py#L546), [test_spark_adapter_ranges.py:128](../../dq/tests/test_spark_adapter_ranges.py#L128)). Preserve v1 compatibility while requiring an explicit admission policy for `no_groups`/`no_values` and same-snapshot population checks; silently flipping v1 would invalidate existing evidence ([ADR-004:56](../decisions/adr/ADR-004-grouped-metric-requests.adoc#L56), [ADR-005:41](../decisions/adr/ADR-005-value-range-metrics.adoc#L41)).

**BET 3 — UNSOUND**

The emitted DDL executes and can be reapplied on PostgreSQL 14.20, but equal start times return two latest rows and both views expose multiple namespaces despite SPEC-006's filtering promise ([postgres_sink.py:128](../../dq/postgres_sink.py#L128), [SPEC-006:51](../specs/SPEC-006-tenant-namespaces.adoc#L51)). Define authenticated query scoping, deterministic recency, and evidence completeness before treating these views as an admission surface; `completed` currently denotes transaction completion, not a passing quality verdict ([postgres_sink.py:258](../../dq/postgres_sink.py#L258), [dq_framework.py:236](../../dq/dq_framework.py#L236)).

**BET 4 — UNSOUND**

The handoff's premise is inaccurate: both file and catalog branches write the same namespace-enriched frame, including newly created catalog tables ([sinks.py:154](../../dq/sinks.py#L154), [sinks.py:167](../../dq/sinks.py#L167)). An existing table lacking that column raises `INSERT_COLUMN_ARITY_MISMATCH` after the file write has already succeeded, making this a migration and partial-persistence defect rather than merely inconsistent query results ([sinks.py:161](../../dq/sinks.py#L161), [test_sinks.py:200](../../dq/tests/test_sinks.py#L200)).

**BET 5 — RISKY-WITH-MITIGATION**

Per-run sink construction is sufficient for the current facade, which constructs its sink inside each invocation ([dq_framework.py:195](../../dq/dq_framework.py#L195)). However, a controlled shared-instance overlap committed run A's artifact inside run B after A rolled back, so enforce exclusive scope ownership or return a run-bound writer before exposing shared sinks to a service ([postgres_sink.py:271](../../dq/postgres_sink.py#L271), [postgres_sink.py:288](../../dq/postgres_sink.py#L288)).

**BET 6 — RISKY-WITH-MITIGATION**

The dependency direction is sound, but the locally inspected closed repository declares `data-quality-framework >=2.3.0`, which is an unbounded lower bound rather than a reproducible pin ([dq-control-plane/pyproject.toml:10](../../../dq-control-plane/pyproject.toml#L10), [ADR-009:43](../decisions/adr/ADR-009-open-core-boundary.adoc#L43)). Release and verify a compatible OSS artifact/schema before promoting its closed consumer, with a locked dependency and explicit migration contract; fixing the publishing environment alone does not establish that compatibility ([ADR-009:107](../decisions/adr/ADR-009-open-core-boundary.adoc#L107), [SPEC-007:17](../specs/SPEC-007-sqlalchemy-arrow-sink.adoc#L17)).

## Wrong-path assessment

- **Kernel semantic versioning — NO:** preserve the shipped fingerprints and compose certified subplans under a new ruleset envelope rather than replacing their contracts (F07; [plan.py:399](../../dq/plan.py#L399)).
- **ranges/v1 — YES:** fulfilling the stated exact-stored-value guarantee would change existing float decisions and therefore requires a new semantic version and recertification (F09; [ADR-005:56](../decisions/adr/ADR-005-value-range-metrics.adoc#L56)).
- **groups/v1 vacuous pass — NO:** an explicit admission no-data policy can protect new consumers without rewriting compatible v1 evidence (F08; [plan.py:508](../../dq/plan.py#L508)).
- **Open-core split — NO:** the dependency boundary is viable, but managed operational value must be validated rather than inferred from closed source (F13; [ADR-009:34](../decisions/adr/ADR-009-open-core-boundary.adoc#L34)).
- **PG evidence schema — YES:** timestamp identity, unbound artifacts, and positional idempotency require schema/API changes before shipping dependent query and metering units (F01–F05; [postgres_sink.py:117](../../dq/postgres_sink.py#L117)).
- **MVP-1/2 ladder — NO:** evidence first and managed service second remains viable if marketplace acceptance requirements are specified now and arbitrary-RDBMS expansion is removed from the immediate critical path (F12–F14; [ADR-007:31](../decisions/adr/ADR-007-productization-mvp.adoc#L31)).

## Top 3 actions before MVP-1 build-out

1. **Amend ADR-006 and SPEC-001/006 around one authoritative execution identity and sealed evidence manifest.** Correct run/artifact joins, stable retry identity, tenant-qualified retention, admission query scoping, and catalog migration before committing consumers to today's schema; F01–F06 undermine the product's central evidence guarantee.
2. **Amend ADR-004/005 with ruleset composition, explicit no-data admission, and an honest float representation contract.** Preserve existing semantic fingerprints while adding complete-ruleset receipts and threshold-sensitive certification; F07–F09 otherwise turn individually valid rule outcomes into misleading dataset-level assurance.
3. **Re-scope ADR-007/009/010 and SPEC-005/007 into a PostgreSQL pilot followed by one supported marketplace offer.** Pin and certify the OSS/closed interface, validate the paid operational promise, and specify entitlement, metering, audit, and recovery contracts before service implementation; F11–F14 are dependency and revenue risks that packaging alone cannot resolve.
